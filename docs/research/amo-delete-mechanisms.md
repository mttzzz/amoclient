## 2. Сырые ответы по типам (копипастопригодные вызовы + суть ответа)

### tasks — нет публичного удаления

```php
// Candidate A: v4 raw DELETE
$this->amoClient->http->delete("tasks/{$taskId}");
// → 403 Forbidden: {"title":"Forbidden","type":"https://httpstatus.es/403","status":403,"detail":"Invalid scope"}

// Candidate B: ajax bulk-delete (по аналогии с leads/contacts/companies) — роута не существует
$this->amoClient->ajax->postForm('/ajax/tasks/multiple/delete/', ['ID' => [$taskId]]);
// → 404, HTML-страница "Здесь ничего нет, только бескрайний космос" (amo generic 404, не JSON)

// Candidate C (принят, но это не delete): пометка выполненной
$taskEntity = $this->amoClient->tasks->find($taskId);
$taskEntity->is_completed = true;
$taskEntity->result = ['text' => 'sp0-spike-closed'];
$taskEntity->update();
// → 200, задача помечена is_completed=true, но продолжает существовать и быть выбираемой по id
```

**Вывод:** 403 "Invalid scope" (не 404) означает, что сам эндпойнт, вероятно, существует в API, но текущий OAuth-виджет не имеет прав на него (или для задач delete-скоуп в принципе не выдаётся сторонним интеграциям) — в любом случае для этой библиотеки/аккаунта недоступен. Teardown полагается на удаление родительского lead.

## 3. Корзина vs hard delete

**Вывод: ajax-`multiple/delete/` для leads/contacts/companies — soft delete (корзина), не физическое удаление.**

Проверено эмпирически на lead 33286097 (полный цикл: create → ajax-delete → find → withOnlyDeleted):
- Обычный `find($id)` после удаления возвращает `[]` — сущность не видна в штатных запросах.
- `leads->withOnlyDeleted()->filterId($id)->get()` **находит** запись с `is_deleted: true`, `account_id`, `updated_at` и полным `_links.self` — то есть запись физически жива в базе amo, просто скрыта из обычных выборок.

На contacts (48892015) и companies (48892017) проверено то же самое частично: `find()` после ajax-delete тоже возвращает `[]` (согласуется с lead-паттерном); `withOnlyDeleted()`-аналог для contacts/companies не проверялся отдельно (модели `Contact`/`Company` могли не иметь этого метода — не проверял, см. открытые вопросы), но нет оснований полагать, что механизм отличается от lead.

**Практическое следствие для teardown (Task 5):** teardown, реализованный через существующий ajax `multiple/delete/`, не оставляет "видимого" мусора в обычном интерфейсе/API-выборках amo (что и требовалось — не мешать реальной работе с аккаунтом), но НЕ уменьшает физически число записей в аккаунте — они уходят в 30-дневную (по документации amo, не проверялось эмпирически) корзину. Если для teardown критична именно **физическая** очистка (а не просто "не мешает"), этого публичный API не даёт — сущность нельзя пробить дальше корзины ни одним найденным вызовом.

## 5. Открытые вопросы

1. **Точный TTL корзины (soft-delete) не проверялся** — не выяснено эмпирически, через сколько дней amo физически purge-ит `is_deleted=true`-записи (документация заявляет ~30 дней, но задача явно просила не доверять доке; без повторного захода через месяц это не подтвердить в рамках спайка).
2. **`withOnlyDeleted()`-эквивалент для Contact/Company не проверялся отдельно** — не установлено, есть ли у моделей `Contact`/`Company` такой же метод, как `Lead::withOnlyDeleted()`; полагаюсь на аналогию с lead (та же ajax-семантика delete), но не подтверждено напрямую списком.
3. **catalogElements: правильная форма ajax-запроса для точечного удаления элемента не найдена** — перепробован один осмысленный вариант (400, "Код ошибки 222"), дальше не итерировал ради экономии зондов на боевом аккаунте. Если Task 5 обязательно нужно точечное удаление элемента (без сноса всего каталога) — потребуется ещё один заход перебора форм запроса.
4. **tasks: 403 "Invalid scope" не отличает "эндпойнта нет" от "нет прав у виджета"** — не выяснено, есть ли способ (другой OAuth-скоуп/права виджета) включить `DELETE /tasks/{id}`, либо он в принципе не публикуется amo для сторонних интеграций.

## 6. Приватный ajax — подтверждённые механизмы (захват 22.07.2026)

**Источник:** запрос удаления задачи снят владельцем из своего браузера (боевой UI amo), остальное — наши
собственные проверки в аккаунте `16117840` на зондах с префиксом `capture-`.

**Это опровергает три вывода §1/§2:** tasks, notes и calls объявлены там «неудаляемыми» — они удаляемы,
просто не публичным v4, а приватным эндпойнтом. Строки §1 по этим типам считать устаревшими.

### Эндпойнт

```
POST /private/notes/edit2.php     (Content-Type: application/x-www-form-urlencoded)
```

### Минимальный контракт (проверен эмпирически)

Снятый из UI запрос содержит **избыточное**: query-параметры `parent_element_id`/`parent_element_type`
и дублирующие поля тела `ELEMENT_ID`/`ELEMENT_TYPE`. Проверено прямым сравнением на четырёх зондах
(две задачи, два примечания): полная форма и минимальная дают одинаковый результат.

```php
/* Достаточно ровно этого — родителя указывать не нужно, amo резолвит его по ID сущности */
$this->amoClient->ajax->postForm('/private/notes/edit2.php', ['ID' => $taskId, 'ACTION' => 'TASK_DELETE']);
$this->amoClient->ajax->postForm('/private/notes/edit2.php', ['ID' => $noteId, 'ACTION' => 'NOTE_DELETE']);
```

Ответ в обоих случаях: `{"status":"ok","id":<id>}` (HTTP 200, `application/json`).

### Каталог глаголов

| Тип | ACTION | Проверено |
|---|---|---|
| tasks | `TASK_DELETE` | ✅ зонды 46711305, 46711379, 46711381 — исчезли из выборки задач аккаунта |
| notes | `NOTE_DELETE` | ✅ зонды 316925537, 316925757, 316925759 — `notes->get()` родителя пуст |
| calls | `NOTE_DELETE` | ✅ зонд 316925779 — **звонок в amo это note особого типа**, снимается тем же глаголом |

Звонок при создании автопривязался к существующей компании `45389979` по совпадению телефона; удалена
только сама note-звонок, компания не тронута.

### Ключевое для архитектуры: авторизация

Эндпойнт **работает под Bearer-токеном самой библиотеки** — браузерная сессия (`session_id`, `csrf_token`)
не нужна. Проверено запуском из PHP через штатный `Ajax::postForm()` (он шлёт `X-Requested-With: XMLHttpRequest`
и `Authorization: Bearer`), а не только из авторизованного браузера. То есть приватный канал доступен либе
на тех же правах, что и публичный v4 — разница не в авторизации, а в стабильности контракта.

### Осталось снять

| Тип | Что нужно |
|---|---|
| catalogElements | точечное удаление элемента списка (сейчас только каскад через удаление каталога) |
| unsorted | «Отклонить» **без** создания сделки (публичный `decline()` порождает лид в скрытом пайплайне) |
| leads/contacts/companies | удаление **насовсем** (текущий ajax кладёт в корзину) + очистка самой корзины |
| shortLinks | адресуемость (в ответе `create()` нет `id`) |

### pipelines (воронки) — публичного хватает, приватный не нужен

Захват владельца из UI: `POST /ajax/v1/pipelines/delete`, тело `request[id]=<id>`.
В терминах либы и с проверкой альтернативы:

```php
/* приватный (как делает UI) — работает под Bearer-токеном либы */
$this->amoClient->ajax->postForm('/ajax/v1/pipelines/delete', ['request' => ['id' => $pipelineId]]);
// → 200 {"response":{"11128450":true,"server_time":1784703545}}

/* публичный v4 — делает то же самое и доступен нам */
$this->amoClient->http->delete("leads/pipelines/{$pipelineId}");
// → 204 No Content
```

**Вывод для архитектуры:** это первый тип, где приватный канал избыточен — публичный v4 умеет удалять воронки
(204). Правило для новой либы: приватный ajax подключаем только там, где публичного механизма нет, иначе мы
без нужды завязываемся на нестабильный контракт. У самой либы сейчас `Pipeline` вообще не имеет `delete()` —
дыра в покрытии, а не отсутствие механизма.

## 7. Захват через UI + опровержения спайка (22.07.2026, вторая волна)

Снято кликами в боевом UI под авторизацией владельца, каждый механизм затем **перепроверен под
Bearer-токеном либы** на собственных зондах.

### 7.1 catalogElements — точечное удаление есть

Спайк не нашёл форму запроса и оставил только каскад «снести весь каталог». Настоящий механизм — отдельный
эндпойнт, а не вложенность в `/ajax/v1/catalogs/set/`:

```php
$this->amoClient->ajax->postForm(
    '/ajax/v1/catalog_elements/set/',
    ['request' => ['catalog_elements' => ['delete' => [$elementId]]]]   // список, можно пачкой
);
// → {"response":{"catalog_elements":{"delete":{"catalog_elements":{"1772365":{...}},"errors":[]}},"server_time":…}}
```

Ответ перечисляет удалённое поимённо и несёт свой `errors[]` — частичный успех тут выражается не HTTP-кодом,
а содержимым `errors`. Для новой либы это отдельный класс ответа: «200, но не всё».

### 7.2 leads — UI-удаление это тот же вызов, что уже есть в либе

```php
$this->amoClient->ajax->postForm('/ajax/leads/multiple/delete/', ['ID' => [$leadId]]);
// → {"status":"success","message":"Удаление прошло успешно для 1 сделки"}
```

Кнопка «Удалить сделку» в карточке шлёт ровно это (`ID[]=33286161`). **Отдельного «удалить навсегда» в UI
нет**, раздела «Корзина» в интерфейсе тоже нет.

### 7.3 Корзина: модалка amo врёт

Диалог подтверждения обещает «Все данные… будут удалены. Восстановить удалённые данные будет невозможно».
Фактически это **soft delete**: удалённый через UI лид `33286161` сразу после удаления виден через
`leads->withOnlyDeleted()` с `is_deleted: true`. Hard delete не выставлен нигде — ни в UI, ни в публичном v4,
ни в приватном ajax. Единственная доступная семантика удаления для leads/contacts/companies — «в корзину».

### 7.4 ОПРОВЕРЖЕНИЕ: «Недостаточно прав для удаления сделки» — это не про права

Спайк (§4) объявил лид `33286105` неудаляемым по правам и оставил как незакрытый хвост; та же ошибка
воспроизводилась и под сессией владельца с полными admin-правами.

Проверка: удалил через UI лид `33286161` (успех, `status:success`), тут же повторил тот же ajax-вызов на нём —
ответ `{"status":"fail","errors":["Недостаточно прав для удаления сделки"]}`. То есть **amo отдаёт этот текст
на попытку удалить уже лежащее в корзине**. Проверено на трёх лидах, включая заведомо свежеудалённый.

Для новой либы это прямое требование: классификатор обязан различать «нет прав» и «уже удалено» — иначе
идемпотентный teardown будет ложно падать на второй попытке. Текст ошибки амо здесь дезинформирует.

### 7.5 ОПРОВЕРЖЕНИЕ: `decline()` не оставляет мусора

Спайк утверждал, что `decline()` порождает настоящий лид, который «надо трекать и удалять отдельно», и что
он неудаляем. Живой цикл (создать sip-unsorted → `decline($uid, $userId)`) показал другое: порождённый лид
(`33286177`, воронка `742990` — **не** архивная) **сразу лежит в корзине** (`is_deleted: true`). Отдельная
уборка не нужна и невозможна (см. §7.4 — повторное удаление отдаёт «fail»).

Практический вывод: `decline()` штатен, трекать порождённый лид в TestEntityRegistry не требуется.

### 7.6 Итоговая таблица teardown (актуальная)

| Тип | Механизм | Семантика |
|---|---|---|
| leads / contacts / companies | `ajax /ajax/{type}/multiple/delete/` + `ID[]` | корзина (soft), повтор = «fail» |
| tasks | `ajax /private/notes/edit2.php` + `ID`,`ACTION=TASK_DELETE` | удаление |
| notes | там же, `ACTION=NOTE_DELETE` | удаление |
| calls | там же, `ACTION=NOTE_DELETE` (звонок = note) | удаление |
| catalogs | `ajax /ajax/v1/catalogs/set/` + `request[catalogs][delete]` | удаление (каскадом уносит элементы) |

| pipelines | публичный v4 `DELETE /leads/pipelines/{id}` → 204 | удаление |
| webhooks | `unSubscribe()` (v4) | hard delete |

### 7.7 Что осталось открытым

- **Purge корзины недоступен вообще** — ни UI, ни API. Сущности живут в `is_deleted: true`; заявленный
  амо TTL ~30 дней эмпирически не проверялся.
- **Жёсткость удаления notes/tasks/calls не проверена**: `{"status":"ok"}` и пропажа из выборок ≠
  доказательство hard delete; аналога `withOnlyDeleted()` для них в API нет.
- **contacts/companies**: корзинная семантика принята по аналогии с leads (тот же эндпойнт), отдельным
  зондом через `withOnlyDeleted()`-аналог не подтверждена.

## 8. Зонды семантики повторного удаления (лид, 22.07.2026)

Снято лидом против аккаунта `16117840` по трём вопросам контракта `Deleter`, на которые нельзя
ответить чтением кода. Все зонды помечены маркером свипа, хвосты убраны (каталоги `6873`, `6875`,
лид `33286479` — снесены проверкой уборки).

### 8.1 Приватный роут на повторное удаление отвечает HTTP 400 без текста

```
POST /private/notes/edit2.php  ID=46712131  ACTION=TASK_DELETE
первый раз  → HTTP 200  {"status":"ok","id":46712131}
повторно    → HTTP 400  {"status":"fail","id":46712131}
```

Ключевое: «уже нет» приходит **ошибочным HTTP-статусом**, а не полем в теле 200, и текста в ответе
нет вовсе — только эхо id. Значит для tasks/notes/calls признак идемпотентного повтора — связка
`(400, status=fail, id совпадает с запрошенным)`, и распознавать его нужно ДО того, как ретрай-конвейер
превратит 400 в исключение. Матч по тексту здесь невозможен физически.

### 8.2 «Недостаточно прав» — общий ответ, а тип сущности в нём враньё

```
POST /ajax/contacts/multiple/delete/   ID[]=48892339
первый раз → HTTP 200 {"status":"success","message":"Удаление прошло успешно для 1 контакта"}
повторно   → HTTP 200 {"status":"fail","errors":["Недостаточно прав для удаления контакта"],
                       "message":"Недостаточно прав для удаления"}

POST /ajax/companies/multiple/delete/  ID[]=48892341
первый раз → HTTP 200 {"status":"success","message":"Удаление прошло успешно для 1 контакта"}
повторно   → HTTP 200 {"status":"fail","errors":["Недостаточно прав для удаления контакта"],
                       "message":"Недостаточно прав для удаления"}
```

Компания в обоих сообщениях названа **контактом** — и в успехе, и в отказе. Отсюда два правила:
дискриминатор матчится по префиксу «Недостаточно прав для удаления» (или по короткому `message`),
никогда по полной строке; и тип сущности из сообщения amo выводить нельзя ни при каких условиях.
Подтверждает §7.4: у сделки формулировка та же с суффиксом «сделки».

### 8.3 `request[catalogs][delete]` списка не принимает

```
POST /ajax/v1/catalogs/set/  request[catalogs][delete]=[6873,6875]
→ HTTP 500, тело — HTML-страница ошибки amo (не JSON)
```

Списочная форма роняет бэкенд amo в 500. Рабочая форма — только скаляр, по одному запросу на каталог
(как и заложено в контракте). Побочно: amo отдаёт на 500 **HTML**, а не JSON — то есть парсер ответа
обязан переживать не-JSON тело, иначе поверх настоящей ошибки ляжет вторая, парсерная.

### 8.4 Следствие для архитектуры

«Уже нет» выглядит по-разному в каждом из трёх каналов: приватный роут — `400 + status:fail`;
`multiple/delete` — `200 + status:fail + русский текст`; `set/`-семья — `errors[].code === 404`.
Три разных представления одного факта — ровно тот случай, когда знание обязано жить в одном месте
(`src/Deleter.php`), а не растекаться по вызывающим: teardown, свип и потребитель библиотеки не должны
знать ни одного из трёх.

### 8.5 Видимость лида в корзине (зонд гейта teardown)

```
лид 33286485 создан → /ajax/leads/multiple/delete/ → HTTP 200 «Удаление прошло успешно для 1 сделки»

leads->filterId(33286485)->get()                    → []
leads->withOnlyDeleted()->filterId(33286485)->get() → [{id:33286485, is_deleted:true, name:null,
                                                       price:null, status_id:null, updated_at:…}]
```

Два вывода для проверок уборки. Первый: обычная выборка удалённого лида отдаёт **пустой массив**, а не
запись с флагом, — значит инвариант «не активен» проверяется именно пустотой ответа. Второй, менее
очевидный: `withOnlyDeleted()` в паре с `filterId()` работает (в ресёрче раньше снимался без фильтра),
но возвращённая запись содержит почти одни `null` — живут `id`, `is_deleted`, `updated_at`, `account_id`.
Проверять в корзине что-либо, кроме id и флага, нельзя: имени там уже нет, и ассерт на маркер в имени
упадёт не потому, что уборка сломалась.

### 8.6 Приватный роут отвечает по-разному ЗАДАЧЕ и ПРИМЕЧАНИЮ/ЗВОНКУ

Форма ответа на повторное удаление, снятая на задаче (§8.1), на примечание и звонок **не
распространяется** — проверено зондом, а не аналогией:

```
POST /private/notes/edit2.php  ACTION=NOTE_DELETE  ID=316929037 (примечание)
первый раз → HTTP 200  {"status":"ok","id":316929037}
повторно   → HTTP 200  {"status":"no note","id":316929037}

POST /private/notes/edit2.php  ACTION=NOTE_DELETE  ID=316929039 (звонок, note_type=call_in)
первый раз → HTTP 200  {"status":"ok","id":316929039}
повторно   → HTTP 200  {"status":"no note","id":316929039}

для сравнения, ЗАДАЧА (§8.1): повторно → HTTP 400 {"status":"fail","id":…}
```

Один роут, один глагол, соседние типы — и два разных представления «уже нет»: у задачи ошибочный
статус без текста, у примечания и звонка успешный статус со словом `no note`. Звонок ведёт себя как
примечание, что подтверждает «звонок = note особого типа» уже и на пути удаления.

Итого «уже нет» существует в **четырёх** видах: `400 + status:fail` (задача), `200 + status:"no note"`
(примечание, звонок), `200 + status:fail + русский текст` (leads/contacts/companies),
`errors[].code === 404` (`set/`-семья). Классификатор, распознающий три из четырёх, тем самым ломает
идемпотентность на четвёртом — и ломает молча, потому что бросок выглядит как честная ошибка.

### 8.7 Сортировка на роуте примечаний есть, но неверное направление amo глотает молча

```
GET /api/v4/leads/notes?limit=50&order[updated_at]=asc      → 200, первые id 7471853, 7471855, 7471857
GET /api/v4/leads/notes?limit=50&order[updated_at]=desc     → 200, первые id 316917451, 316917449, 316897255
GET /api/v4/leads/notes?limit=50&order[updated_at]=nonsense → 200, выдача как при asc, ошибки нет
```

Два вывода. Первый практический: дискавери, идущая окном по `updated_at` (примечания, звонки, задачи),
обязана запрашивать **`desc`** — наши записи всегда самые свежие, и при возрастающем порядке они лежат
ровно в хвосте, отрезаемом потолком страниц. На пустом тестовом аккаунте это незаметно (в окне трёх
суток всего 2 примечания), на нагруженном — систематический промах именно по собственному мусору.

Второй — про доверие к параметрам: **неверное направление сортировки amo не отвергает**, а отвечает 200
и молча сортирует по умолчанию. Опечатка в направлении не проявится ни ошибкой, ни предупреждением —
только тем, что уборка перестанет находить хвосты. Ещё один случай, когда отсутствие сигнала
неотличимо от исправной работы.
