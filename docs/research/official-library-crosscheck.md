## 1. Сортировка (task/notes)

### Официальная либа

`TasksFilter` и `NotesFilter` (`src/AmoCRM/Filters/TasksFilter.php`, `NotesFilter.php`) оба
используют один и тот же generic-механизм: `OrderTrait` + `HasOrderInterface`
(`src/AmoCRM/Filters/Traits/OrderTrait.php:20` — `setOrder(string $field, string $direction = 'asc')`).
Валидации имени поля НЕТ вообще — `$field` любая строка, библиотека просто кладёт её в
`$filter['order'][$field] = $direction`. Никакого enum/whitelist по сущностям в коде не существует —
значит на уровне библиотеки список «разрешённых полей сортировки» **не объявлен и не
проверяется**: она безразлична к тому, поддержит ли amo-бэкенд конкретное поле.

Вывод по либе: она не подтверждает и не опровергает наш замер — она просто не в курсе. Расхождения
с ней нет, потому что сравнивать не с чем.

### Официальная документация

`tasks-api`: «Доступные поля для сортировки: **created_at, complete_till, id**.» — `updated_at`
в списке НЕТ.

`events-and-notes` (примечания): «Доступные поля для сортировки: **updated_at, id**.»

### Наш зонд (из брифа лида)

- `/api/v4/tasks`: `order[updated_at]` игнорируется целиком (asc/desc/мусор — одна и та же
  страница, HTTP 200); работают `order[id]`, `order[created_at]`, `order[complete_till]`.
- `/api/v4/leads/notes`: `order[updated_at]` работает.

### Вывод

**Полное совпадение, документация не врёт** — редкий случай, когда все три источника сходятся.
Официальная документация ТОЧНО перечисляет ровно те поля, которые наш зонд нашёл рабочими для
tasks (`created_at`, `complete_till`, `id`), и явно ИСКЛЮЧАЕТ `updated_at` — то есть у tasks
`updated_at` не «сломан», а никогда не был заявлен как сортируемое поле; amo молча игнорирует
незаявленное поле вместо ошибки (сам факт молчания — по-прежнему наша находка, доки её не
описывают). Для notes документация подтверждает `updated_at` как штатное сортируемое поле —
ровно то, что показал зонд. Расхождений нет, самое ценное здесь — точная атрибуция причины
поведения tasks к недокументированности поля, а не к багу.

## 2. Удаление

### Официальная либа

`HasDeleteMethodInterface` (`src/AmoCRM/EntitiesServices/HasDeleteMethodInterface.php`) —
маркерный интерфейс `deleteOne()`/`delete()`. Полный список файлов, которые его реализуют:

```
Chats/Templates.php, Customers/Statuses.php, Customers/Transactions.php,
CustomFieldGroups.php, CustomFields.php, EntityFiles.php, Files.php,
Leads/LossReasons.php, Leads/Pipelines.php, Leads/Statuses.php, Roles.php, Sources.php
```

Отсутствуют в списке — и, проверено отдельно, **нет ни одного упоминания `delete`/`Delete` в
файле вообще** (не только интерфейса, вообще никакого delete-кода, даже заглушки с
`NotAvailableForActionException`): `Leads.php`, `Contacts.php`, `Companies.php`, `Tasks.php`,
`EntityNotes.php`, `Calls.php`, `Catalogs.php`, `CatalogElements.php`.

`Webhooks.php` — отдельный случай: не реализует `HasDeleteMethodInterface`, но имеет свой
`unsubscribe(WebhookModel $model): bool` (`Webhooks.php:145`) — `DELETE` на тот же метод с телом
`toUnsubscribeApi()`, ответ `$result['result']`.

`Pipelines::deleteOne()` (`Leads/Pipelines.php:171`) — `DELETE {method}/{id}`, `$result['result']`.
`Sources::deleteOne()`/`delete()` (`Sources.php:45,62`) — та же форма, плюс батч-вариант
`delete(BaseApiCollection)` шлёт `DELETE` с телом-коллекцией (в отличие от Pipelines — у нашего
`Deleter`/§8.3 каталоги списком не принимаются, но у sources в офиц. либе списочный DELETE есть;
не проверял эмпирически, работает ли он реально — за рамками моего мандата, отдельная гипотеза
для будущего зонда, если понадобится батч-удаление source).

Отдельно ценная находка в `AmoCRMApiRequest::delete()`/`parseResponse()`
(`src/AmoCRM/Client/AmoCRMApiRequest.php:430-494, 642-672`):
- HTTP 204 (No Content) ловится ДО общей проверки статуса и превращается в `AmoCRMApiNoContentException`,
  который `delete()` глотает и возвращает `['result' => true]` (:489-491). Значит успешный delete
  без тела — штатный, ожидаемый случай, а не edge-case для парсера.
- Если тело не-JSON и не пусто и статус не 202 — либа НЕ падает на `json_decode`, а бросает
  `AmoCRMApiException("Response body is not json", $originalStatusCode, ...)` (:661-666), кроме
  429 — для него отдельный `AmoCRMApiTooManyRequestsException` (:654-660). Это прямое
  архитектурное подтверждение факта §8.3/8.4 «парсер обязан пережить не-JSON тело» — официальная
  либа именно так и делает: НЕ пытается парсить HTML как JSON, отдаёт типизированное исключение
  с сохранённым исходным HTTP-статусом.

### Официальная документация

`leads-api`, `contacts-api`, `companies-api` — ни один DELETE-эндпойнт не документирован ни для
одной из трёх сущностей. Все три страницы документируют только `is_deleted: bool` как поле
ответа. `only_deleted`-параметр (значение `with[]` для получения записей из корзины) документирован
**только на странице leads** (пример: `/api/v4/leads?order[updated_at]=asc`, отдельно —
`only_deleted` возвращает «удаленные сделки, которые еще находятся в корзине»); на страницах
contacts/companies такого параметра/примера нет вовсе — только упоминание самого поля `is_deleted`.

`events-and-notes` — ни delete-эндпойнта, ни какого-либо намёка на удаление примечаний.

### Наш зонд / §7.6 research doc

Полностью совпадает с picture выше: leads/contacts/companies — только приватный
`ajax/{type}/multiple/delete/` (корзина); tasks/notes/calls — только приватный
`/private/notes/edit2.php`; catalogs/catalogElements — приватный `ajax/v1/.../set/`;
webhooks — публичный `unSubscribe()`; sources — публичный `delete()`; pipelines — публичный
`DELETE /leads/pipelines/{id}`.

### Вывод

**Совпадает, с одним важным уточнением по corzина contacts/companies.** Официальная либа —
чистое подтверждение таблицы §7.6: где у нас «нет публичного удаления», там у офиц. библиотеки
буквально нет ни строчки кода про delete; где у нас «публичное удаление есть» (webhooks, sources,
pipelines) — оно есть и у них, с той же формой (одиночный DELETE по id/destination). Расхождений
по механике удаления НЕТ.

По corzина-семантике (§7.7, открытый вопрос «contacts/companies — soft-delete принят по аналогии
с leads, отдельно не подтверждён»): **триангуляция даёт смешанный сигнал, вопрос всё ещё открыт,
но не бездоказательно**. `CanReturnDeletedInterface` (`src/AmoCRM/Models/Interfaces/CanReturnDeletedInterface.php`)
с константой `ONLY_DELETED` реализован ВСЕМИ тремя моделями — `LeadModel`, `ContactModel`,
`CompanyModel` (все три — `implements CanReturnDeletedInterface`, все три перечисляют
`self::ONLY_DELETED` в `getAvailableWith()`). Т.е. **код официальной либы утверждает, что
`with=only_deleted` работает для contacts/companies так же, как для leads** — это гипотеза №2 по
уровню доверия, сильнее, чем ничего. Но официальная ДОКУМЕНТАЦИЯ этого не подтверждает: страницы
contacts/companies знают про `is_deleted`-поле, но не документируют `only_deleted`-параметр вообще
(ни разу не упомянут), тогда как для leads он расписан явно с примером. Наш зонд эмпирически
проверял только leads (§8.5). Итог: библиотека (гипотеза) говорит «работает у всех трёх»,
документация молчит про contacts/companies, зонд не проверял. Открытый вопрос §7.7 остаётся
открытым, но теперь с конкретной, проверяемой гипотезой (`with[]=only_deleted` для contacts и
companies) — стоит эмпирической проверки, если/когда понадобится подтверждать corzина-инвариант
не только для leads.

## 3. Лимиты и ретраи

### Официальная документация (`/developers/content/api/recommendations`)

- «не более 7 запросов в секунду на одну интеграцию» и «до 50 запросов в секунду на весь аккаунт».
- HTTP 429 при превышении.
- «при многократном нарушении ограничений, аккаунт блокируется и на любой запрос в API будет
  возвращаться HTTP код 403».
- Рекомендуемый размер пачки сущностей в одном запросе — «не более 50».
- На 504 — «уменьшить количество передаваемых сущностей в запросе и повторить запрос».

### Официальная либа

Ретраев/бэкоффа/`sleep` в библиотеке **нет вообще** — единственное упоминание 429 во всём `src/` —
это бросок типизированного `AmoCRMApiTooManyRequestsException` в `parseResponse()`
(`AmoCRMApiRequest.php:654-660`). Библиотека узнаёт о превышении лимита и типизированно
сообщает об этом исключением, но не троттлит, не ждёт, не повторяет запрос сама — это целиком
ответственность вызывающего кода. `grep -rln "sleep|backoff|retry"` по всему `src/` даёт единственное
совпадение — файл самого класса исключения.

### Наш свип (`AmoTestSweeper.php`)

`DELETE_THROTTLE_US = 150000` (150 мс между delete-запросами) → ~6.67 запр/сек — **под потолком
7 запр/сек на интеграцию**, соответствует рекомендации. `DELETE_BUDGET = 200` — это потолок
суммарных удалений за прогон свипа, не размер одного запроса; с рекомендацией «не более 50
сущностей в одном запросе» не пересекается впрямую, потому что каждое удаление у нас — отдельный
HTTP-запрос с одним id (см. §8.3 — списком catalogs не принимает), а не батч.

### Вывод

**Совпадает.** Троттлинг свипа (150мс = 6.67/сек) вписывается в задокументированный лимит
7 запр/сек на интеграцию с запасом. Официальная библиотека сама никакого троттлинга/ретрая не
делает — значит наш проактивный `usleep` + `DELETE_BUDGET` не «повторяют» какой-то официальный
механизм, а **компенсируют его отсутствие** — это наше собственное, оправданное решение, а не
расхождение с чем-либо. Стоит явно отметить (не блокер, просто для полноты): официальная либа не
делает автоматический retry на 429 вообще, только бросает исключение — если наш `Deleter`/queue-слой
рассчитывает на автоматический ретрай 429 где-то выше по стеку (RetriesTransientAmoErrors и т.п.),
это целиком наша ответственность, официальный образец здесь не помощник.

## 4. Пагинация

### Официальная документация

«Максимальное кол-во возвращаемых сущностей... не более 500, большинство методов возвращает не
более **250** сущностей» — конкретный потолок per-запрос не единообразен по методам, но нигде не
превышает 500 глобально и обычно ≤250.

### Официальная либа

`PagesFilterTrait` (`src/AmoCRM/Filters/Traits/PagesFilterTrait.php`) — `limit` дефолтится в
**50**, `page` в 1, никакого верхнего клэмпа/валидации в коде нет (`setLimit(int $limit)` принимает
что угодно, доверяет вызывающему не превышать серверный потолок).

Отдельно — пагинация «за краем» выражена типизированным исключением
`AmoCRMApiPageNotAvailableException` (`src/AmoCRM/EntitiesServices/Traits/PageMethodsTrait.php:32,55`),
но это относится к `nextPage()/prevPage()` — курсорной навигации по `_links.next/_links.prev` из
ответа коллекции, а не к прямому запросу `page=N`. Наш `AmoTestSweeper::scan()` использует прямой
`page($page)->limit(150)->get()` и трактует пустой ответ как конец — другой, но не
противоречащий механизм (мы не используем `_links`-навигацию вообще, значит
`AmoCRMApiPageNotAvailableException`-эквивалента у нас в принципе быть не может; сравнивать не с
чем в лоб).

### Наш свип

`MAX_PAGES = 10` × `limit(150)` = потолок 1500 записей на тип за скан.

### Вывод

**Совпадает, без противоречий.** `limit(150)` у нас **меньше** и документированного потолка
методов (обычно ≤250), и умолчания официальной либы (50) не нарушает — 150 в пределах
задокументированного максимума. Курсорная (`_links`) пагинация официальной либы и наша
прямая постраничная (`page=N`) — разные, но не конфликтующие механизмы; сравнение
«за краем» неприменимо напрямую, потому что мы этот путь (next/prev ссылки) не используем.

## Итог — самое важное для лида

1. **Сортировка — полное совпадение, документация не врёт.** Офиц. доки tasks-api дословно
   перечисляют `created_at, complete_till, id` (без `updated_at`) — ровно наш зонд. notes —
   `updated_at, id` задокументированы явно, тоже совпадает. Библиотека валидацию полей не делает
   вообще, сравнивать с ней нечего.
2. **Удаление — полное совпадение по механике**, официальная либа буквально не содержит ни строчки
   delete-кода там, где мы нашли «нет публичного удаления» (tasks/notes/calls/catalogs/leads/
   contacts/companies), и содержит — там, где мы нашли публичный путь (webhooks/sources/pipelines).
   Плюс архитектурное подтверждение §8.3/8.4: офиц. либа тоже трактует не-JSON тело типизированным
   исключением, не пытаясь парсить HTML как JSON — тот же принцип, который нужен `Deleter.php`.
3. **Новая, конкретная гипотеза по corzина contacts/companies** (§7.7 всё ещё открыт): код офиц.
   библиотеки утверждает `with=only_deleted` работает для contacts/companies не хуже, чем для
   leads (`CanReturnDeletedInterface` реализован всеми тремя моделями), но публичная документация
   этого не описывает вовсе для contacts/companies — стоит эмпирической проверки, если понадобится
   закрыть §7.7 окончательно.
4. **Лимиты/ретраи и пагинация — наши числа консервативнее рекомендаций**, расхождений нет;
   официальная либа сама не троттлит и не ретраит 429 — это ответственность вызывающего кода
   везде, в том числе у нас.
